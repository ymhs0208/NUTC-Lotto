# SQLite 千人本機驗證（2026-10-17）

此次修改將學生登入及 Session 資料庫工作的等待上限改為 1024，兩者同時工作上限仍為 16；密碼雜湊上限不變。只有在學生登入尚未開始處理就因佇列額滿或等候逾時被拒絕時，API 才回傳 `loginRetrySafe: true`，讓前端依 Retry-After 與隨機延遲重試，最多兩次。

## 方法與結果

- 本機 Node v26.10.0、真實暫存檔案 SQLite、單一應用程式程序。
- 1000 個合成學生帳號，使用獨立 Cookie，回傳專題須與各自帳號相符。
- 先分批建立 1000 條 keep-alive 連線，再一起送出登入；成功登入後一起查詢。
- 未啟用校網模式；1000 次登入均使用本機相同 IP，未達現有 1200 次／15 分鐘額度。
- 未重試任何失敗登入；未呼叫正式環境或使用正式名冊。
- 共用模式合併雜湊驗證；個別模式關閉合併，每次登入都執行真實 scrypt。合成資料沿用測試密碼與雜湊。
- Node 雜湊工作上限為 8；沒有設定 `UV_THREADPOOL_SIZE` 覆寫。

| 模式 | 登入成功 | 登入 p50 | 登入 p95 | 登入 p99 | 登入最長 | 查詢成功 | 查詢 p95 |

| 共用密碼 | 1000/1000 | 299 ms | 299 ms | 300 ms | 300 ms | 1000/1000 | 87 ms |
| 個別密碼 | 1000/1000 | 20003 ms | 38907 ms | 40535 ms | 40949 ms | 1000/1000 | 101 ms |

兩種模式登入與查詢均為 HTTP 200，無 429、503 或傳輸失敗。整個登入加查詢階段分別耗時 413 ms 與 41078 ms。這是單次開發機測量，期間有其他驗證工作執行，數字不是效能承諾。

```sh
npm run test:load -- --users=1000 --mode=shared
npm run test:load -- --users=1000 --mode=individual
```

初次直接瞬間建立 1000 條本機 TCP 連線時，出現 871 筆 ECONNRESET；改為預先分批建立連線後，才得到上表結果。因此本測試驗證既有連線上的登入尖峰，不涵蓋 TCP／TLS 連線建立尖峰。

## 適用範圍

**這不是 Cloudflare 正式環境的千人容量證明。** 本機測試不包含 Workers 的 API 物件分流、共用限流物件儲存延遲、遠端資料庫 binding、平台 CPU／記憶體上限、真實校網與網路延遲；本次 Workers 整合測試也不是千人壓測。

正式使用前，須以獨立 Workers 測試部署與合成帳號測試共用／個別密碼、相同校網出口、登入及查詢混合負載、同時管理員抽籤，並記錄成功率、p95／p99、429／503／逾時及平台資源使用。等待佇列只能緩衝尖峰，不能增加密碼驗證或集中資料庫的吞吐量。

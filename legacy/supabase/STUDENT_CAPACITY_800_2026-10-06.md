# 800 人容量檢查

2026-10-06（臺灣時間）。測試目前工作目錄版本，不修改容量設定、不部署、不連接正式資料庫。測試行程啟用 `CAMPUS_NETWORK_ONLY=true`，同一來源 IP、800 個合成學號，每次模擬 Supabase HTTP 請求延遲 100 ms。各情境依序執行，連線預熱；共用密碼驗證快取起初為冷快取。個別密碼模式走每次 scrypt 驗證路徑，不使用共用驗證快取。

目前未通過「800 人同時登入及同步查詢，每次皆成功」的驗證。四個情境首次登入皆為 784／800，其餘 16 次回 503。測試工具待首波登入及查詢結束後，再等 Retry-After 並重試一次，才達到 800／800 登入。這不是 800 人首輪皆成功，也不是前端自動登入重試的證據。

| 平台／密碼模式 | 首次登入成功 | 成功登入 P95 | 800 人同步重新查詢成功 |
|---|---:|---:|---:|
| Node／共用 | 784／800 | 10.039 秒 | 528／800 |
| Workers／共用 | 784／800 | 11.418 秒 | 576／800 |
| Node／個別 | 784／800 | 34.817 秒 | 528／800 |
| Workers／個別 | 784／800 | 87.563 秒 | 576／800 |

每個情境補完登入後，登入後首次查詢合計 800／800；同步重新查詢是另一次獨立 800 人波次。皆無結果錯配、各有 800 個獨立 Cookie，未遇到 429。

## 容量界限與失敗

登入同一 process／isolate 最多 16 件執行、768 件等待，共 784 件。Session 資料庫工作最多 16 件執行、512 件等待，共 528 件，還需與 session 建立／刪除共享。這是同一時刻容納的工作數，並非全域人數限制或固定吞吐量；Workers 有多個 isolates，且請求到達時間會影響實際結果。

Node 共用密碼同步查詢：528 次 200、172 次 503、100 次傳輸錯誤；個別密碼：528 次 200、272 次 503。Workers 共用密碼：576 次 200、113 次 503、111 次傳輸錯誤；個別密碼：576 次 200、14 次 503、210 次非 JSON 500，訊息為 Network connection lost。

503 符合排隊／資源保護；本機連線重設與 Workers 非 JSON 500 的來源尚未完整定位，不能直接歸因正式後端或認定正式環境會有相同錯誤數。Workers 共用／個別測試另有 17／2 次工具內部的陳舊連線重送；Node 個別測試為 1 次，Node 共用為 0。

同步查詢測試沒有套用瀏覽器端讀取 API 遇到 503 後的一次自動重試，所以表中失敗數不能直接當成最終畫面失敗人數；也不能假設重試一定成功。

## 判斷

800 人總使用者數與 800 人同時送出請求不同。分散時間操作的正式容量尚未驗證；目前明確不宜承諾 800 人同時登入／查詢都一次成功。即使校網模式免除學生 IP 額度，登入排隊、資料庫工作與密碼驗證成本仍存在。

若要以 800 人同時使用作為上線目標，需將登入及 session 等待容量留出餘裕，重新驗證等待期限、資源使用和同步查詢連線問題，再用正式等效學校主機／Supabase／校園網路壓測。只放寬限流或增加排隊數不代表已達標；个別密碼的 Workers 登入時間也是獨立瓶頸。

測試資料位於 `security/evidence/campus-network-800-{node,workers}-{shared,individual}.json` 及對應 runtime log。所有結果來自本機 mock Supabase，不含正式 PostgreSQL CPU／I/O、校園網路、WAF 或前端初次下載，不能作正式容量保證。
